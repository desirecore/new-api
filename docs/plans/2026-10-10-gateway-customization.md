# desirecore 模型网关定制需求

日期：2026-10-10
状态：需求记录；具体方案分项评审，尚未实施

## 目标与约束

new-api 作为 desirecore 的模型网关，持续支持本产品的专用功能与 UI 定制，同时尽可能保持官方上游 API、数据结构和升级路径的兼容性。遵守 `AGENTS.md` 与 `docs/fork-maintenance.md`，不把长期定制默认视为临时补丁。

本阶段分两项工作，分别设计、验证与上线。当前先聚焦第一项，不修改 desirecore-server。

## 一、按分组查看模型链路

用户需求：以分组为管理入口，直观看到每个分组有哪些模型，以及这些模型的渠道链路、渠道优先级与权重、模型重定向和访问指标，优先提供可视化。

- 使用现有 new-api 分组；不另建一套模型归属或路由配置。
- 导航层级为“分组 → 模型 → 优先级层 → 渠道 → 映射后的模型”。页面沿用“模型”用语。
- 用户已认可交互式链路图方向：分组选择器 + 图形画布 + 详情抽屉；默认模型链路树，可切换共享渠道网络，表格辅助。支持展开/折叠、缩放/平移、搜索定位和路径高亮。
- 不依赖模型库登记；模型库仅作为可选的描述、图标等补充。
- 同时保留禁用渠道、没有启用渠道的模型、没有流量的配置，避免只展示成功流量。
- 分开表达配置拓扑、普通选择规则、实际历史流量与单次请求追踪，避免把权重当作实际命中率。
- 首先采用新增只读模块，不修改请求分发、重试、映射和计费路径，不新增持久化表。
- 详细设计见 `2026-10-10-group-model-routing-design.md`。

## 二、业务后台控制额度、分组与账单同步

用户需求：通过 desirecore 业务后台更方便、可靠地控制用户额度和分组，并同步模型账单。

### 已核实的现状

参考仓库：`/Users/liyongsheng/Projects/desirecore-server`。

- `apps/cloud-api/src/newapi/quota.ts`：按业务账本余额计算绝对 quota，再通过 `/api/user/manage` 的 override 覆盖网关钱包；失败后标记 pending 并重试。
- 修改用户分组与 Token 分组需要读取原对象后带回其他字段更新，两次同步独立执行，存在部分成功状态。
- `apps/cloud-api/src/newapi/usage-logs.ts`、`usage-sync.ts`：分别分页拉取消费与退款日志，使用日志 ID 游标回写账本；消费按 owner 聚合并保留 quota 换算余数。
- 用量统计是独立链路：只读 MySQL 日志，聚合到业务数据库的 `usage_daily`，不等同于资金账本。
- 相关文档仍含“stock NewAPI、不二开”的旧约束；本仓库的新政策不能自动视作另一仓库已更新决策。

### 推荐保留的职责边界

- desirecore 管用户/团队身份、套餐权益、现金与积分账本；资金账本继续作为业务真相源。
- new-api 管模型路由、计费规则执行、实时额度限制、消费与退款事实。
- 不在两个系统同时维护独立的套餐资金池，避免重复授信或重复扣款。

### 后续设计范围

1. 专用分组更新接口：只修改指定字段，明确用户与 Token 范围、权限、同步结果及失败补偿。
2. 额度同步协议：幂等操作标识、版本和消费确认边界，处理充值/到期/扣减与网关并发消费、预扣、结算、退款，避免旧余额重新覆盖已发生的消费。
3. 稳定账单增量接口：消费与退款统一获取，支持持久事件标识、重放、确认与追赶积压；普通管理日志不能默认充当可靠账单事件源。
4. 同步可观测：最后成功时间、同步延迟、pending、重试、差异与修复记录。
5. 逐步减少业务后台对网关 MySQL 日志表结构的直接依赖，兼容现有统计链路后再迁移。

同步时效尚未由用户选定。当前候选方向为“网关本地扣费，业务账本秒级最终一致”与“每次请求由业务账本预先授权”；设计此项时单独确认，不作为模型链路视图的前置条件。

任何新的可靠事件机制都必须核实结算写入与事件持久化的原子性、主库与独立日志库边界，不能仅凭 webhook 重试或自增 ID 宣称不漏账。

## 推进顺序

1. 评审并实施分组模型配置链路视图。
2. 补充已有数据能支持的访问指标；完整尝试追踪另行设计。
3. 独立评审业务后台集成协议，再协调两个仓库改造。
